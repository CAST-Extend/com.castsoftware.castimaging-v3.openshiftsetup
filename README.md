# Documentation
This repository contains the helm chart to deploy CAST Imaging on an OpenShift cluster.
General concepts about CAST Imaging install can be found here: https://doc.castsoftware.com/imaging/install/global/kubernetes/

## Helm Chart Release Notes

### 3.6.9 (vs 3.6.8)

#### New Features
- **MCP Server 3.1 (`imaging-mcp-server` 3.1.0)**: the `mcp-server` pod now runs the MCP Aggregator Gateway with the Structural, Semantic search and Text2Cypher MCP servers behind it (see https://doc.castsoftware.com/imaging/mcp-server/imaging/3.1/docker/). Requires CAST Imaging ≥ 3.6.8. `McpServer.enable` still defaults to `false` (and is ignored when `Viewer.enable: false`).
- **Analysis-node autoscaling (opt-in, disabled by default)**: `AnalysisNodeAutoscaling.enabled: true` adds analysis nodes when queued jobs exceed the free capacity of the running nodes, and removes idle ones afterwards. A node running an analysis is never removed. Requires CAST Imaging 3.6.9 and the OpenKruise operator. Enabling it restarts the analysis nodes once. The autoscaler pod runs under the `restricted-v2` SCC (no fixed UID). On a single-node cluster (Single Node OpenShift, OpenShift Local / CRC), set `AnalysisNodeAutoscaling.allowNodeRead: false`. See [Analysis-node autoscaling](docs/analysis-node-autoscaling.md), section "On OpenShift", for requirements, settings and troubleshooting.
- **`ServiceAccountName` option** (empty by default): name of an existing ServiceAccount to run all Imaging pods and Jobs with. For example, it can carry its own `imagePullSecrets`, or be granted a specific SCC.
- **Custom labels & annotations**: labels and annotations can now be added to every resource deployed by the chart (Deployments, StatefulSets, Jobs and their pods, PVCs, Services, ConfigMaps, Secrets, Routes, ServiceAccount, Roles/RoleBindings, StorageClass), e.g. for network micro-segmentation, monitoring or inventory tools. New `values.yaml` settings, merged in this order (the last one wins for a given key):
  - standard labels generated by the chart on all resources when `standardLabels: true` (`false` by default): `app.kubernetes.io/name` (component name, e.g. `console-postgres`), `app.kubernetes.io/instance`, `app.kubernetes.io/version`, `app.kubernetes.io/managed-by`, `app.kubernetes.io/part-of: castimaging` and `helm.sh/chart`. They are not added to the Service / workload selectors;
  - `commonLabels` / `commonAnnotations`: all the resources;
  - `resourceMetadata.<type>.labels` / `.annotations`: all the resources of a type (`deployment`, `statefulSet`, `job`, `pvc`, `service`, `configMap`, `secret`, `route`, `serviceAccount`, `rbac`, `storageClass`). `deployment` / `statefulSet` / `job` values also apply to their pods;
  - `componentMetadata.<component>.labels` / `.annotations`: all the resources of a component (e.g. `console-postgres`, `viewer-neo4j`; the list is in `values.yaml`).

  ```yaml
  commonLabels:
    appcode: APxxxxx
  resourceMetadata:
    deployment:
      annotations:
        oneagent.dynatrace.com/inject: "true"
  componentMetadata:
    console-postgres:
      annotations:
        oneagent.dynatrace.com/inject: "false"
  ```
  Keys managed by the chart (`app`, `imaging.service`, `haproxy.router.openshift.io/*`, `helm.sh/*`...) cannot be set, and unknown types / components are rejected (helm fails with an explicit message).
  ⚠️ **Note**: the StatefulSets `volumeClaimTemplates` (`castdir` PVCs of console-analysis-node, `neo4jdata` PVC of viewer-neo4j) are immutable: they only receive the PVC labels/annotations when the StatefulSet is created (first install, or when custom metadata is configured for the first time on a new StatefulSet). On `helm upgrade`, their current labels/annotations are read from the cluster (Helm `lookup`) and kept unchanged; existing PVCs can be labelled manually (`oc label pvc ...` / `oc annotate pvc ...`). With **Argo CD**, which renders the chart without cluster access, add to the Application `ignoreDifferences` on `StatefulSet` `.spec.volumeClaimTemplates` with the `RespectIgnoreDifferences=true` sync option, otherwise the upgrade of an existing StatefulSet is rejected as soon as these values change.
  Changing these values restarts the pods and re-runs the init Jobs (their name includes a hash of the values).
- **Configurable security contexts**: the `securityContext` of all the pods (Deployments, StatefulSets, Jobs) and containers (including init containers) can now be set, e.g. to use for instance a fixed `runAsUser` or `fsGroup` when a policy engine (Gatekeeper, Kyverno...) rejects the IDs assigned by OpenShift from the namespace range (e.g. `fsGroup: 1001270000` outside `1-65535`). New `values.yaml` settings, merged in this order (the last one wins for a given key):
  - the security context already set by the chart (unchanged when nothing is configured);
  - `podSecurityContext` / `containerSecurityContext`: all the pods / all the containers;
  - `componentSecurityContext.<component>.pod` / `.container`: the pods / containers of a component (same component names as `componentMetadata`).

  Sub-keys (`seccompProfile`, `capabilities`...) are merged key by key, and a `null` value removes a key set by the chart (e.g. `runAsNonRoot: null`).
  ```yaml
  podSecurityContext:
    runAsUser: 1001
    fsGroup: 1001
  ```
  ⚠️ **Do not set `runAsGroup`**: when `runAsGroup` is not set, OpenShift runs the containers with the root group (GID 0) as primary group. Some images (like `console-postgres` or `console-analysis-node`) need it, because some of their directories can only be written by the root group. With `runAsGroup`, these containers lose GID 0 and fail. If `runAsGroup` is required, add `supplementalGroups: [0]`.
  ⚠️ **Note**: the SCC granted to the service account must allow these IDs. The default `restricted-v2` SCC only allows the namespace range: use e.g. `nonroot-v2` (or a custom SCC), or change the namespace annotations `openshift.io/sa.scc.uid-range` / `openshift.io/sa.scc.supplemental-groups`. The pod-level settings (`fsGroup`, `runAsGroup`, `supplementalGroups`) also apply to the containers injected by other operators (e.g. Dynatrace `oneagent` init container).

#### Configuration Changes
- **New default `GATEWAYSERVICE.SPRING_CLOUD_GATEWAY_SERVER_WEBFLUX_TRUSTEDPROXIES: ".*"`**: console-gateway-service 3.6.9 is built on Spring Cloud Gateway 5. It no longer forwards `X-Forwarded-*` headers to the backend services unless `trusted-proxies` is set. Without it, console-authentication-service never learns that the original request was `https://`, so it builds an `http://` OAuth2 login callback URL and the browser is sent back to `http://` after login. The value is a regex matched against the IP of the client calling console-gateway-service (with Routes, the OpenShift router). It can be restricted to the router pod network (e.g. `"10\..*"`).
  ⚠️ **Migration note**: if you use your own `values.yaml`, add this setting under `GATEWAYSERVICE`. The OpenShift router already sets `X-Forwarded-Proto` / `X-Forwarded-Host`. If a reverse proxy or load balancer sits in front of the router, it must forward the original `X-Forwarded-Proto` / `X-Forwarded-Host` headers.
- **Init Jobs renamed on each change**: `postgres-init-job`, `custom-postgres-init-job` and `keycloak-init-job` now get a short hash suffix (e.g. `keycloak-init-job-1a2b3c4d`). The hash changes with the chart version, the values or the Job's script. A Job's pod template is immutable, so `helm upgrade` now creates a new Job and removes the old one, instead of failing to patch it. They also retry up to 3 times (`backoffLimit: 3`, previously 0 or the default), as their scripts are idempotent.
- `imagePullSecrets` (when `UseImagePullSecrets: true`) is now also set on the console-postgres StatefulSet and on the init Jobs.

#### Fixes
- **Keycloak init Job more robust**: `init-keycloak.sh` now retries the admin token request (up to 60 times, every 5s), as Keycloak can answer while its database is still restarting. The realm admin role is now always (re)assigned to the `KCADMIN_USERNAME` user, even when the user already exists. This repairs a previous run that created the user but failed before assigning the role.
- **Analysis nodes and databases protected from cluster-autoscaler eviction**: the console-analysis-node, console-postgres and viewer-neo4j pods now carry the `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"` (honored by the OpenShift cluster autoscaler) and `karpenter.sh/do-not-disrupt: "true"` annotations. A cluster autoscaler therefore never evicts them to remove an under-used worker.
- **Backup / restore scripts** (`ImagingBackup`, `ImagingRestore`, `.sh` and `.bat`): large files are transferred in chunks, each one size-checked and retried. A new `BACKUP_POSTGRES` setting skips the Postgres backup/restore (e.g. with `CustomPostgres`). Neo4j databases are discovered from the backup instead of being hardcoded. The analysis-node autoscaler and OpenKruise StatefulSet are supported. See [ImagingBackupRestore.md](ImagingBackupRestore.md).
- `Util-ScaleDownAll` / `Util-ScaleUpAll` take the namespace as first argument (default `castimaging-v3`), and handle the analysis-node autoscaler.

### 3.6.8 (vs 3.6.7)

#### New Features
- **Configurable network timeouts**: two new `values.yaml` settings control how long a request may take on the OpenShift Route before the router aborts it with a Gateway Timeout (504). They are applied through the `haproxy.router.openshift.io/timeout` annotation when `Routes.enable=true`:
  - `NetworkTimeoutSeconds: 300`: `castimaging-route` (main application, to `console-gateway-service`). Increase this if you see timeouts on long-running calls.
  - `ExtendProxy.timeoutSeconds: 3600`: `extendproxy-route` (bundle uploads can be large/slow, hence the much higher default).

  Previously no timeout annotation was set, so the OpenShift router default (30s) applied.
- **Persistent log volumes for console services**: logs of console-control-panel, console-gateway-service, console-authentication-service, console-service, console-sso-service and console-dashboards are now written to dedicated PersistentVolumeClaims (`pvc-controlpanel-logs`, `pvc-gatewayservice-logs`, `pvc-authenticationservice-logs`, `pvc-consoleservice-logs`, `pvc-ssoservice-logs`, `pvc-dashboards-logs`, created with `helm.sh/resource-policy: keep`), so they survive pod restarts. Their sizes are configurable via the new `size_controlpanel_logs`, `size_gatewayservice_logs`, `size_authenticationservice_logs`, `size_consoleservice_logs`, `size_ssoservice_logs` and `size_dashboards_logs` values (default `2Gi` each). Keycloak (sso-service) is configured to log both to the console and to a daily-rotated file (`sso.log`, max 10M per file).
  Volume write permissions rely on the `fsGroup` assigned by the OpenShift SCC (`restricted-v2`), so no fixed `fsGroup` is set in the chart.
- **`Viewer.enable` option** (default `true`): set it to `false` to skip the deployment of the Viewer components and their related resources: viewer-neo4j, viewer-server, viewer-etl, viewer-api, viewer-aimanager and mcp-server (Services, Deployments/StatefulSet, the `servernginxconf` ConfigMap and the `pvc-imagingviewer-v3-*` PersistentVolumeClaims). When `Viewer.enable: false`, `McpServer.enable` is ignored and the mcp-server is not deployed.
  ⚠️ **Note**: on an existing deployment, switching to `Viewer.enable: false` does not delete the Viewer PersistentVolumeClaims (they are created with `helm.sh/resource-policy: keep`).

#### Security
- **`guest` database user removed**: the embedded Postgres init script no longer creates the `guest` user, and the `guest-db-password` key has been removed from the `imaging-pwd-sec` Secret (`GuestDbPassword` value no longer used). Console services now connect explicitly with the `operator` user (`DB_USER` / `DB_USERNAME`, `DB_DATABASE=postgres`); console-authentication-service additionally receives `DB_ENCRYPTED_PASSWORD` from the `operator-db-password-crypted2` Secret key.
  ⚠️ **Migration note**: `GuestDbPassword` can be removed from your custom `values.yaml`, and the `guest-db-password` key is no longer required in an `existingSecret`. On existing deployments, the `guest` user already present in Postgres is not dropped by the upgrade (it can be removed manually with `DROP USER guest;` if not used elsewhere).

#### Configuration Changes
- **Deployment strategy set to `Recreate`** on console-authentication-service, console-service, console-control-panel, console-gateway-service, console-sso-service, mcp-server, viewer-aimanager, viewer-api, viewer-etl and viewer-server (previously the default `RollingUpdate`).
- Image updates: all CAST Imaging application images 3.6.8.

### 3.6.7 (vs 3.6.6)

#### New Features
- **Proxy exclusions auto-update job**: a new `proxy-exclusions-update-script` ConfigMap and a suspended `proxy-exclusions-cronjob` CronJob are shipped with the chart. It can be triggered manually (`oc create job proxy-exclusions-cronjob-<id> --from=cronjob/proxy-exclusions-cronjob -n <namespace>`) to refresh `control_panel.settings.non_proxy_hosts` from the subnets of currently registered services, when `proxy_settings_mode` is `MANUAL_PROXY`.
- New `AIMANAGER.SUMMARY_LOG_LEVEL: info` default environment variable.

#### Security
- **`UseCustomTrustStore` removed**: self-signed or otherwise unverifiable certificate on an internal service is no longer a blocking issue. The `UseCustomTrustStore` option and the `auth.caCertificate` value have been removed from `values.yaml`, along with the `authcacrt` ConfigMap and the associated init container/volume mounts in `console-authentication-service`.
  ⚠️ **Migration note**: if your existing `values.yaml` sets `UseCustomTrustStore` / `auth.caCertificate`, you can remove them: they are no longer used by the chart.

#### Fixes
- **`license-extend-update-script.sql` fixed**: `extend_url` is now only auto-populated when currently empty, so a manually-configured Extend URL is no longer overwritten on every `helm upgrade`. Updating `extend_apikey` no longer depends on `ExtendProxy.enable`.

### 3.6.6 (vs 3.6.5)

#### New Features
- **Health probes** added on viewer-api, viewer-etl, viewer-server and viewer-aimanager (startup/liveness/readiness) for better detection of pods stuck at startup.
- **Generic per-service environment variable injection**: new sections in `values.yaml` (`NEO4J`, `ETL`, `SERVER`, `API`, `AIMANAGER`, `MCPSERVER`, `CONTROLPANEL`, `ANALYSISNODE`, `AUTHENTICATIONSERVICE`, `CONSOLESERVICE`, `DASHBOARDS`, `GATEWAYSERVICE`, `SSOSERVICE`, `EXTENDPROXY`) allowing custom environment variables to be added to each container without touching the templates.

#### Security
- The operator's encrypted password (`DB_ENCRYPTED_PASSWORD`) is no longer injected in plain text into the console-control-panel deployment: it is now stored in the Kubernetes Secret and referenced via `secretKeyRef`.
- ⚠️ **Migration note**: if you use an external `existingSecret`, it must now also contain the `operator-db-password-crypted2` key (base64-encoded value of the `CRYPTED2:...` string), in addition to the previously required keys.

#### Configuration Changes
- Neo4j memory parameters (`NEO4J_server_memory_heap_initial__size`, `NEO4J_server_memory_heap_max__size`, `NEO4J_dbms_memory_transaction_total_max`) have moved from the root of `values.yaml` into the `NEO4J:` section — update your custom values files accordingly.
- `IMAGING_DOMAIN_SYNCHRO_ENABLED` removed as a dedicated variable; it is now set via the `CONTROLPANEL:` env section instead (default unchanged).
- ⚠️ **Audit-trail volume no longer used**: the dedicated `pvc-controlpanel-audit-trails` PersistentVolumeClaim is no longer created or mounted by console-control-panel. Audit trail data is now stored in the existing shared volume (mounted at `/opt/cast/shared`) instead of its own volume (audit-trail full path remains unchanged: /opt/cast/shared/common-data/audit-trail).
  For customers upgrading from a previous version: the old PVC is **not deleted** by the upgrade (it was created with `helm.sh/resource-policy: keep`) — it simply becomes unmounted/orphaned, and its data (including the `audit-trail` folder) remains intact on the underlying disk. If you want to recover the audit trail history it contained, mount it temporarily with a pod and copy the data out, e.g.:
  ```yaml
  apiVersion: v1
  kind: Pod
  metadata:
    name: audit-trail-recovery
    namespace: <namespace>
  spec:
    restartPolicy: Never
    containers:
      - name: init-util
        image: castimaging/init-util:1.2.11
        command: ["sleep", "3600"]
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 200m
            memory: 128Mi
        volumeMounts:
          - name: audit-trails
            mountPath: /opt/cast/shared/common-data
    volumes:
      - name: audit-trails
        persistentVolumeClaim:
          claimName: pvc-controlpanel-audit-trails
  ```
  ```
  oc apply -f audit-trail-recovery.yaml -n <namespace>
  oc cp <namespace>/audit-trail-recovery:/opt/cast/shared/common-data/audit-trail ./audit-trail-backup
  oc delete pod audit-trail-recovery -n <namespace>
  ```

#### Fixes
- Fixed NodePort/LoadBalancer activation conditions on the gateway service and extendproxy.

#### Known Issues
- Only applies to Kubernetes deployments: the application export/import feature is not yet functional in this version (it will fail). It will be fully functional in the next release.
